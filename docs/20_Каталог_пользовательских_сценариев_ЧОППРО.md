# Каталог пользовательских сценариев ЧОППРО · актуализация 09.10.2026

Сценарии сохраняют исходные ID. Текущее поведение уточнено по этапам 2–4; непроверенные production и организационные условия отражены в матрице. Доставка уведомлений исключена из текущего рабочего объема, внутренние события сохраняются. Полевой протокол и финальная приемка еще требуются.

## UC-01. Подключение ЧОПа

Сценарий прямо указан в исходном ТЗ заказчика.

1. Оператор платформы создает организацию, владельца, модули и ограничения ресурсов; автоматический денежный биллинг не заявляется.
2. Владелец активирует приглашение и настраивает MFA; организационные документы и основания обработки ПДн подтверждаются заказчиком отдельно.
3. Организация импортирует поддерживаемые CSV-ресурсы по версии шаблона; конкретные бухгалтерские поля и импорт 1С требуют образца заказчика.
4. Система показывает ошибки импорта и формирует протокол.
5. Администратор назначает роли, создает посты и публикует первую неделю графика.

## UC-02. Заступление на смену

Сценарий прямо указан в исходном ТЗ заказчика.

1. Охранник открывает мобильное приложение и видит ближайшую принятую смену.
2. Кнопка заступления использует допустимое окно назначения; сервер проверяет настроенные время и допуски.
3. Приложение запрашивает координаты, точность и скан QR-кода объекта/поста.
4. Сервер сравнивает время, геозону, устройство, назначение и QR-токен.
5. При успешной проверке смена переходит IN_PROGRESS; при аномалии событие требует проверки.
6. При отсутствии заступления после порога система создает внутренний риск NO_SHOW; доставка уведомления исключена из текущего объема.

## UC-03. Офлайн check-in

Сценарий прямо указан в исходном ТЗ заказчика.

1. Приложение проверяет наличие заранее загруженной смены и QR-контрольной точки.
2. Событие сохраняется локально с UUID, временем устройства, координатами, точностью и порядковым номером.
3. Пользователь видит статус «Ожидает синхронизации».
4. После восстановления связи очередь последовательно доставляет события и вложения с ключами идемпотентности; повтор не создает дубликат.
5. События с большой задержкой или аномалиями попадают в очередь ручной проверки.

## UC-04. Происшествие

Сценарий прямо указан в исходном ТЗ заказчика.

1. Охранник выбирает категорию и серьезность, добавляет текст/голос, фото и принятые меры.
2. Критическое происшествие отправляется немедленно, даже если часть необязательных полей не заполнена.
3. Система сохраняет внутренний статус критического происшествия и контроль действий; доставка цепочки уведомлений исключена из текущего объема.
4. Начальник проверяет, дополняет и публикует разрешенную часть заказчику.
5. После выполнения действий происшествие закрывается с обязательным итогом.

## UC-05. Ежемесячный отчет заказчику

Сценарий прямо указан в исходном ТЗ заказчика.

1. Система собирает покрытие постов, часы, обходы и опубликованные происшествия за период.
2. Ответственный проверяет черновик и исключает внутренние данные.
3. После публикации отчет получает неизменяемую версию и становится доступен заказчику.
4. Заказчик скачивает PDF и при необходимости подтверждает ознакомление.

## FLOW-01. Обход по контрольным точкам

Дополнительный демонстрационный сценарий, сформированный из требований исходного ТЗ.

1. Охранник открывает назначенный обход.
2. Приложение показывает маршрут и контрольные точки.
3. Охранник сканирует QR каждой точки; фиксируются время и геоданные.
4. Пропуск/аномалия формирует статус для проверки.
5. Руководитель видит итог обхода.

## FLOW-02. Истечение документа сотрудника

Дополнительный демонстрационный сценарий, сформированный из требований исходного ТЗ.

1. Ежедневная задача пересчитывает статус документа.
2. При достижении порога документ получает EXPIRING.
3. Создается одно внутреннее событие контроля на соответствующую ступень; канал доставки не подключается.
4. Кадровик открывает карточку документа и видит срок/историю.
5. После загрузки новой версии выполняется ручная проверка.

## FLOW-03. Ограничение доступа по tenant и объектам

Дополнительный демонстрационный сценарий, сформированный из требований исходного ТЗ.

1. Пользователь авторизуется в tenant.
2. Сервер формирует tenant context из доверенной сессии.
3. RBAC проверяет atomic permission.
4. Object scope ограничивает список объектов.
5. Запрос к чужому tenant отклоняется и фиксируется в security log.

## FLOW-04. Ручная проверка аномального check-in

Дополнительный демонстрационный сценарий, сформированный из требований исходного ТЗ.

1. Событие check-in получает REQUIRES_REVIEW.
2. Начальник объекта открывает очередь проверки.
3. Исходное событие отображается без изменения.
4. Руководитель принимает решение и указывает причину.
5. Создается отдельный MANUAL_OVERRIDE и запись аудита.

## FLOW-05. Публикация отчета и подтверждение заказчиком

Дополнительный демонстрационный сценарий, сформированный из требований исходного ТЗ.

1. Ответственный формирует черновик отчета.
2. Перед публикацией проверяется отсутствие внутренних данных.
3. Публикация создает неизменяемую версию.
4. Заказчик открывает опубликованную версию.
5. При подтверждении ознакомления фиксируются пользователь, дата и версия.

## FLOW-06. Перезапуск мобильной очереди

Рабочий сценарий этапа 3; проверен автоматически, дополнительно требует физических устройств.

1. Охранник загружает назначения и маршрут до потери сети.
2. Без сети создает отметку и происшествие с фото/аудио.
3. Закрывает и повторно открывает приложение; сессия и зашифрованная очередь восстановлены.
4. Возвращает сеть и повторяет синхронизацию; исходное время и вложения сохранены, дублей нет.
5. Проверяет состояния доставки и результат в кабинете администратора.

## FLOW-07. Резервная копия и контрольное восстановление

Рабочий сценарий этапа 4; production-объем и RPO/RTO требуют отдельного протокола.

1. Оператор платформы создает зашифрованную копию БД и приватных файлов с причиной операции.
2. Проверяет целостность и отдельно сохраняет копию.
3. В изолированном контуре подтверждает восстановление, проверяет записи и связанные файлы.
4. Фиксирует время, RPO/RTO и результат, включая поведение при ошибке.
5. Подтверждает регулярный cron и мониторинг без посетителей.
